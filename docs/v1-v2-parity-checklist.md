# V1 → V2 機能パリティ チェックリスト（載せ替え判定用）

V1（`LegalBridge_AI_GCP`）の機能をV2（`apps/legalbridge`）と照合し、**V1を撤去してV2へ載せ替えられるか**を判定するための対照表。V1の実装（`src/pages`, `services/api/src`, `SYSTEM_REQUIREMENTS.md`）を確認して作成。

## 凡例

| 記号 | 意味 |
|---|---|
| ✅ | V2実装済み・稼働可 |
| 🟡 | V2実装済みだが**既定OFF**（有効化＋実地検証が必要） |
| 🔶 | **部分的**（V1の一部機能のみ移植） |
| ❌ | **V2未移植**（載せ替え前に対応 or 廃止判断が必要） |

## 載せ替え判定サマリ

**✅ できている（V2で回せる）**：マスタ管理・文書生成/確定/PDF/Drive・条件明細/消化実績/検収・契約取込/アウト条件・検索・認証。→ **日常のドキュメント/マスタ/条件業務はcutover可能。**

**🚧 cutover前に判断が要る（大）**：
1. **金銭・ロイヤリティ管理（Bブロック）** — 支払報告書・ロイヤリティ計算・源泉税・請求。V1の主要価値の一つで**V2未移植**。ここを止められるか／部分的にV1を残すかの経営判断が必要。
2. **Backlog双方向（Fブロック）** — V2は読取のみ。書き戻し運用に依存しているなら要移植。
3. **外部連携の実地点火（Eブロック）** — 実装済みだが未検証。

**🧹 廃止 or 後回しの棚卸しが要る（中〜小）**：作品権利モデルの詳細タブ群（C）、データ品質/名寄せ/Excel/LegalOn取込（D）、稟議・スニペット・アーカイブ・ガイド（G）。**「V1で使っているが実は不要」なものを廃止判定**すれば載せ替え範囲が縮む。

### 推奨cutover順序

1. **今回デプロイした③④コードを本番投入**（全OFF）→ Aブロックを実データ受け入れ
2. この表を**関係者レビュー**し、B/C/D/Gの各項目を「移植する／V1に残す／廃止」に仕分け
3. **B（金銭管理）の扱いを決定** ← 最重要
4. 外部連携（E）を1つずつ有効化・検証
5. 仕分け結果の「移植」項目を実装 → 全部○になったら本番V2昇格・トラフィック切替

---

*このチェックリストはV1リポジトリの実装（`src/pages`・`services/api/src`・要件定義）とV2の現状を突き合わせて作成。各項目の「移植/残す/廃止」欄は関係者記入用。*
