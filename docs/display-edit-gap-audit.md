# 表示・編集ギャップ監査（2026-08-11）

発端：条件明細の「相手方」がブランクのまま直せない、という指摘。
「**表示はあるのに編集手段がない**」「**参照・書込ロジックが欠けていて常にブランク**」を
全画面×全フィールドで棚卸しした（読取専用の監査エージェント3系統で全クライアント画面 →
ルート → SQL → 書込文の全数トレース）。本書はその統合結果と、第1波で入れた修正、残課題の優先順位。

## 根本構造（ほぼすべての指摘の源泉）

1. **`condition_lines`（条件明細）は全コードで追記専用だった。** UPDATE 文が1つも存在せず、
   取込・アウト条件で書いた料率・金額・相手方等は以後永久に不変。データ品質センターは
   「未リンク条件明細（severity: high）」を検出するのに修復手段がゼロだった。
2. **V1 遺産データの NULL FK**（相手方・作品・文書）が LEFT JOIN で無言の「—」になり、
   未設定なのか該当なしなのか判別できなかった。
3. **API は対応済みなのに UI に入力欄が無い**フィールド群（案件担当者・タスク担当・
   作品の権利者・契約マスタの更新通告/アラート/見直し期日）。
4. **`parent_license_condition_id` は全 INSERT に含まれない** → 請求の「未リンク」バッジ・
   債権マップの上流分配・契約チェックの当該指摘は V2 データでは構造的に常時発火。

## 第2波で修正済み（2026-08-11・スキーマ整合×フロー順×視認性の再監査）

**視認性（全画面底上げ）**：基本入力スタイル新設（生ブラウザ入力欄12画面・入力文字11〜12px縮小の解消）、
ヒント共通化と --ink-faint のコントラスト是正（2.5→4.6:1）、checkbox 縦積みバグ、サイドバー幅を無視した
ブレークポイント（1050〜1260px幅で横はみ出し）、フォームグリッドの auto-fit 化（文書作成223px→約350px等）、

**フォーム消失バグ**：受付番号1キー入力ごとのフォーム全消去（デバウンス＋非破壊マージ）、台帳・担当者の
検索でフォーム消失、金額方式切替での入力消去、下書き画面の破壊的操作の一等地配置。

**データ正確性**：受付番号既定値 VALIDATION-1 廃止、金額欄クリア→0円確定バグ、ウィザード追記アウト条件の
無言素材#1紐付け、取引先「種別」自由入力→選択式（源泉徴収は「個人」完全一致判定のため）、Sell-Off期間の

計算方式選択肢に PER_UNIT/INSTALLMENT 欠落、作品区分の「未設定」戻しが無視される問題、
Slack ID 小文字貼り付けの自動大文字化、主要フォームへの maxLength 付与。

**画面間フロー**：確定文書の matter_id 自動設定（受付番号→案件解決・全確定文書が案件から孤児だった）、
文書詳細に「案件を開く」、受領記録の条件行ID手入力解消（条件明細詳細「受領を記録」＋一覧行「記録」で

権限のない画面への空リンク非表示、停滞理由の新規時非表示。

## 第3波で修正済み（2026-08-11・日常運用2フロー監査：依頼→文書→送付／支払資料→送付）

- **送信・署名履歴の永続表示**：GET /documents/:id/send-history を新設（Gmail送信履歴＋CloudSign依頼履歴）。
  文書詳細の外部連携に履歴パネルを表示し、CloudSign は保存済み文書IDでリロード後もステータス照会可能に。
- **宛先・署名者の候補表示**：確定時に解決済みの documents.vendor_id → 取引先マスタのメール/担当者名を
  候補ボタンで提示（admin/legal のみ・従来は毎回手打ち）。
- **メール送信の文書なし防止**：Drive 未保存の文書は送信ブロック（本文に文書URLが入らないため）。
- **送信の自動記帳**：Gmail送信・CloudSign依頼の成功時、文書に案件が紐付いていれば
  lb_v2_matter_sends に自動記録（channel email/cloudsign。手動二重記帳を廃止）。SEND_CHANNELS に cloudsign 追加。
- **同テンプレ連続作成で前の文書の値が残る問題**：フォームを開くたびにリマウント（formNonce）。
- **行き止まり導線**：案件の関連文書の行→文書詳細（メール/CloudSign送信へ）を直接開ける。
  確定成功パネルに「案件を開く（送付記録へ）」（finalize 応答に matterId 追加）。
  常に「未実行/停止」と表示される固定ステータス表を撤去。
- **重複送信の判別**：既送信（冪等スキップ）と今回送信をトーストで区別。
- **法務ロールの空振り防止**：送信/署名依頼は管理者のみのため、法務にはボタンを最初から無効表示＋説明。

## 統合カート（2026-08-12・V1 の MergeCart / MatterMergeCart 移植）

V1 は「籠に集めてから統合先を選ぶ」方式で、課題キー・案件IDの手入力を排していた。
V2 にはこれが無く、案件統合は ID 2つの手入力フォームのみだった。右下常駐のカートを新設：

- **課題カート**（依頼画面「カートに入れる」）：👑で主要課題を選び、
  「新規案件を作成して束ねる」（主要=primary・他=related）／「既存案件へ紐づけ」（案件名検索）。
- **案件カート**（案件詳細「統合カートに入れる」）：👑で残す案件を選び、合言葉入力のうえ
  統合元を順に `/matter-merge` へ流す。失敗した案件はカートに残して再試行できる。
- 保管は sessionStorage（V1 同様タブを閉じれば消える）。画面遷移しても中身は保持。
- サーバ API は既存のまま（`POST /matters`・`POST /matters/:id/issues`・`POST /matter-merge`）＝
  新規グラント・新規スコープなし。

## 残課題（優先順位つきバックログ）

### P1（金額の正しさに直結・要設計判断）
- **条件明細の本体編集**（料率・金額・MG・期間・向き等）：¥・料率の入力ミスが受領計算に永久伝播する。
  monetary データのため、変更履歴（誰がいつ何を）を持つ guarded PATCH として設計すべき。
  条件明細詳細画面が自然な置き場。要：condition_lines の列レベル UPDATE グラント追加＋監査ログ。
- **parent_license_condition_id（上流ライセンス条件リンク）**：書き手ゼロのため分配・債権マップ上流が
  構造的に空。アウト条件追記フォームに「根拠イン条件」選択（UIは既に半分ある）＋既存行の後付けリンク機能。
- **受領記録の訂正 UI**：PUT /condition-receipts/:id は実装・テスト済みだが呼ぶ画面が無い。
  実受領額・期間の入力ミスが現状取り消せない。請求ダッシュボードに編集ボタンを追加するだけで機能する。
- **payments.tax_rate**：受領同期の INSERT が書かないため支払報告書が全行 10% 既定で表示（既定である表示も無し）。

### P2（業務データの完全性）
- **文書の件名・相手方の後付け修正**（form_data 不変・過去文書取込は `{}`）：メタデータ修正 PATCH。
- ~~**取引先の代表者・口座情報**~~ → **2026-08-12 実装済み**：取引先フォームに
  代表者名・法人番号と振込先（金融機関/支店/種別/口座番号/名義カナ/メモ）を追加。
  口座情報は V1 の redact と同じく**管理者のみ**参照・更新でき（GET は非管理者に返さず
  `canEditBank=false`、POST/PATCH/import は口座キーを含むと 403）、クライアントも
  非管理者のときは口座キーを送らない（空文字上書きによる消失を防ぐ）。
  grant 009 が表レベル INSERT/UPDATE のため**追加グラント不要**。
  注意：V1 の 1:N `vendor_bank_accounts` は V2 からは更新しない（V1 は主口座を
  レガシー列へ同期し、1:N が空ならレガシー列から補完するため、V1 停止までの併走中に
  V1 側で口座を編集した取引先のみ表示が食い違いうる）。
- **素材・権利ソース・系譜(work_relations)の削除**：追加のみで誤登録が消せない。
- **document_sends の訂正/削除**：誤記録が永久に残る。

### P3（表示・導線）
- 文書台帳の明細（items 等の配列項目）が詳細で丸ごと非表示／40項目超の無言切り捨て。
- 文書一覧の状態バッジが reissued/superseded を「確定済み」と表示。
- CloudSign/Gmail 送信履歴が DB にあるのに読むルートが無い（リロードで消える）。
- 下書き一覧の文書番号列（常に確定前）・検索プレースホルダの文書番号言及。
- matter_issues の summary_snapshot/note・document_drafts.document_number 等、書き手のない列の整理。
- ContractIntakeWorkspace.tsx（1,079行）はどこからも import されない死コード → 削除候補。
