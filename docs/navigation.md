# 左のメニュー（入口の組み直し）

対象: `apps/legalbridge-v3`（`src/client/nav.ts`・`App.tsx`）

## 1. 区分

2026-11（UI 再構築の手順 2。docs/desk-home.md）から、メニューは 4 項目。今ある画面はどれも消さず、
どれかの項目のタブとして残す（URL・ほかの画面からの飛び先・ブックマークは変わらない）。
タブの多い項目は、タブの並びに小見出し（group）を付ける。

| 項目 | 小見出し | タブ（view。運用はタブ sub まで） |
|---|---|---|
| ホーム | — | home（今日やること + 畳んだ作業台） |
| | 受付 | intake（受付箱）／ daily（デイリータスク） |
| 作業台 | — | desk（取引先・案件・作品のツリーを全幅で） |
| | 台帳 | matters ／ parties ／ works ／ agreements ／ agreement-map ／ conditions ／ documents ／ ringi |
| | 作業 | workbench（取引開始作業）／ deals（入金・取引管理）／ money（支払・お金） |
| 一括処理 | 支払 | paydocs（支払文書）／ closing（まとめて締める） |
| | 登録・作る・送る | ops/imports ／ workbench（sub=orders。発注書 CSV）／ ops/contracts ／ ops/sending |
| | 直す・書き出す | ops/fixes ／ workbench（sub=settled。検収済みの遡及）／ ops/exports |
| 監査・設定 | 点検 | ops/quality ／ condition-check ／ drift |
| | 監視 | flows ／ ops/deadlines ／ rpt |
| | 記録 | ops/audit-report ／ ops/audit |
| | 設定 | ops/snippets ／ statement-models ／ integrations ／ leftovers ／ settings（admin だけ） |

- 同じタブは 2 回並べない（以前は まとめて締める が支払処理作業と一括処理の 2 か所にあった）。
- 運用の画面の見出しは、開いているタブの名前と、そのタブの一言（hint）。
- 受付の件数（受付箱の未処理・更新あり／デイリータスクの残り）は「ホーム」に出す。
- 台帳と作業のタブは、作業台に吸収できたものから外す（docs/desk-home.md §4）。

## 2. 決まりごと

- **画面と URL は変えない。** 項目は今ある画面を束ねるだけ。ほかの画面からの飛び先（`setView`）・古いブックマーク・ホームの札はそのまま動く。
- **最初の画面は URL から決める**（`App.tsx` の `view` の初期値）。以前は home を先に出してから URL の画面へ移っていたので、文書の URL を開き直しただけでホームの盤面の集計（`/home/stations`：10 本の集計）が走り、本番では DB の接続プール（10 本）を塞いで目当ての画面の要求が接続待ち 5 秒で落ちていた。
- **ホームの盤面（`/home/stations`）** は集計を 2 本ずつ順に回し、結果を 1 分覚える（同時に来た要求は 1 回の計算に相乗り。`ops/home-stations.ts`）。
- 項目が 2 つ以上の画面を束ねるときは、画面の上にその切り替え（タブ）を出す。運用（ops）の画面は運用のタブを出さず、見出しを項目の名前にする。
- **光らせる項目** は開いている画面から決める（`activeHub`）。sub（運用のタブ・作業テーブルの一括のモード）まで当たる項目が先、同じ画面が 2 つの項目にあれば最後に押した方、どちらでもなければ先に並ぶ方（まとめて締める → 支払処理作業）。

- 旧 回の一覧（`#/rounds`）は支払文書の「入金と作者への支払」へ転送する（URL も `#/paydocs` に書き換える）。

## 3. 支払処理作業

- 支払文書の一覧の行に **回号**（第 N 回。時限式は締めの seq、イベント式は製造・納品の日の順。`paydocs/rows.ts` の `roundNo`）と、起点の **イベント式／時限式**（旧 能動／受動）を出す。
- 取引管理で許諾先からの入金を「入金を確認した」と押すと、その場に「この入金で作者に払いが出ます」のパネルが開き、作者ごとの報告を起こせる（`ReceiptsForPayment`）。入金済みの行の「作者への支払を見る」からも開く。
- 支払文書の「入金と作者への支払」タブで、入金ごとの作者の状態（未報告・金額が違う・計算書待ち・計算書済）を一覧する（docs/royalty-ledger.md §10）。
- 支払文書の「入金から計算書」タブ（`client/ReceiptSettle.tsx`）：取引モデル（再許諾／自社製造・他社販売／自社製造・自社販売）→ OUT 先（許諾先）→ 条件（作品 × 取引モデル）か記録済みの入金 → 入金日・金額・税込・前金／後金／一括・言語 → 払うべき作者（自動で全員）→「計算書を作る」で 入金の記録 → 作者ごとの報告 → 利用許諾計算書（決定）→ 作者への支払 まで 1 回（docs/royalty-ledger.md §10.1）。「＋ 入金を足す」で前金と後金・別の取引先の入金を並べると、作者ごとに 1 枚（入金 1 件が 1 行）。自社製造・自社販売は OUT 先が無いので作品を選び、数量 × 基準価格 から報告を起こす（入金は記録しない）。

## 4. 一括処理 › まとめて登録・更新する

- 台帳を CSV で入れる・直す入口はここ 1 つ（`client/BulkRegister.tsx`）。対象を 取引先／作品（作品・出版作品・ゲーム作品）／契約（基本契約を直す・既存契約）／条件明細（利用許諾条件・業務委託などを直す）のカードで選び、①ファイルを用意 ②試す ③反映 の順。
- 条件明細の「CSV で一括編集」、作品の「↑作品を一括登録」「↑条件を一括登録」、取引先⇔基本契約の「直した CSV を取り込む」は、ここをその対象で開くボタンだけになった（それぞれの画面に埋め込んでいた取込は外した）。書き出しは元の画面にも残る。

## 5. 作品 › 権利とお金の流れ

- 作品のタブは「作品／権利とお金の流れ／支払文書」。以前の「回と文書」は支払文書のタブの「条件ごと」の見せ方に入れた（「進み順」が支払文書の表）。
- 権利とお金の流れ（`GET /api/v3/works/:id/rights-flow`、`server/works/rights-flow.ts`・`client/WorkRightsFlow.tsx`）：
  - 作者（IN 条件。この作品とその元の作品に付いたもの）／当社の作品の系譜（元の作品・この作品・派生作品）／取引先（OUT 条件。この作品とその派生作品に付いた再許諾・他社販売）を 3 列で。
  - 取引先ごとに「→ 作者A 5%・イラストB 2% に払いが出る」。決まりは台帳・入金のパネルと同じ（同じ利用形態・IN の作品が OUT の作品かその祖先・許諾先専用の条件が勝つ）。
  - お金の流れ（直近 12 か月）：許諾先ごとの入金（入金済み）・作者ごとの許諾料（報告を起こした分）・未処理（作者の報告・計算書が済んでいない入金の件数）。当社に残る額（入金 − 作者への許諾料）は管理者だけに出す。
  - 上の帯に確かめてほしいこと：作者のいない許諾先／ほかの利用形態では払っている作者にこの許諾先から払いが出ない／同じ作者 × 作品 × 利用形態の重複。「条件の点検で直す」で監査へ。

## 6. 監査 › 点検・取り残し › 条件の点検

- `GET /api/v3/conditions-check`（`server/conditions/check-service.ts`・`client/ConditionCheck.tsx`）。5 つの札：
  - 重複：同じ作者 × 作品 × 構成要素 × 利用形態 × 対象の許諾先に生きた IN の条件が 2 本以上。残す条件を選んで「まとめる」（`POST /conditions-check/merge`）：寄せる条件の報告（回から外し、発生日で残す条件の回へ）・予定の行・依頼の繋がりを移し、寄せる条件を無効にする。決定した文書・支払・計算書・共著の取り分のある条件、料率・単価・通貨の違う条件は寄せない。
  - 作品の重複・原作の整理：同じ名前の作品をまとめる／原作を作品の原作名に畳む（docs/work-editions.md §8）。
  - 版元・販売元の条件なし：再許諾・他社販売の刊行物・製品で相手との条件（OUT）が無いもの（docs/work-editions.md）。
  - 決済の型が空：許諾料の条件で settlement_mode が無いもの。いまの推測を出し、その場で 時限式／イベント式 を決められる（`PUT /royalty-ledger/timing`）。
  - 根拠の文書なし：IN の条件で、契約に載っておらず決定済みの文書にも繋がっていないもの。
  - 作者に届かない許諾：再許諾・他社販売の OUT で、効く IN の条件が 1 本も無いもの。

## 7. 業務委託の期日と利用許諾の期間（A-121）

業務委託の期日は契約形式で決まる（`workShapeOf`。`server/conditions/contract-form.ts`）。条件の登録（1 本）と『業務委託（発注）』の両方で同じ。

| 契約形式 | 期日の欄 |
|---|---|
| 請負（・売買） | 納期だけ（成果物が前提）。期間で回数が決まる決済の型を選んだときだけ期間も |
| 準委任（・委任） | 役務提供の開始・終了。成果物「あり」なら納期も |
| 未定 | 期間と納期（契約形式を選ぶと必要な欄だけになる） |
| 許諾（種類がライセンス） | 許諾開始・許諾終了（空なら無期限）。納期は出さない |

- 条件の登録（1 本）は ① で 契約形式 → 成果物（準委任のとき）→ 成果物の権利の帰属先 → 支払の形 の順に選ぶ。見えていない期日は送らない。納期が条件の登録（1 本）で保存されていなかった不具合も直した。
- 受注者帰属の成果物の利用許諾（`LicenseTermsSection`）は、支払の形のすぐ下に **許諾期間**（無期限／有期。有期なら終了日が必須）を置く。納期・役務提供期間とは別の「当社が成果物を使える期間」。その下は、委託報酬に含む・無償なら「許諾の範囲」（利用形態・独占性・地域・言語）、別途なら「許諾条件（許諾料と範囲）」。

## 8. 許諾料の分配（共著・複数の権利者）

条件明細の「許諾料の分配」（`ConditionShares`）は ①誰が分けるか（当社が各人に払う／代表が受け取って分ける）②誰に・どれだけ（契約書の書き方で：料率か割合）③ほかの条件にも の順。行ごとに「例：売上 ¥1,000,000 のとき」の額を出す。

## 9. 作品 › 刊行物・製品（版元／販売元・ISBN／JAN）

作品の下に刊行物・製品（相手・関係・ISBN／JAN・刊行日／発売日・価格・相手との条件）を持つ。関係は 自社／グループ会社（料率なし）／再許諾／他社販売（OEM。ボードゲーム）。出版作品・ゲーム作品の一括登録から入る。詳しくは docs/work-editions.md。

## 10. 作品台帳の検索

作品の絞り込み（`GET /works/tree?q=`・`GET /works?q=`）は、作品名・作品コード・カナに加えて **取引先** でも引く。
作品に付いた生きた条件の相手先（作者・許諾先）、共著の取り分の権利者、刊行物・製品の版元・販売元のどれかが、
名前・カナ・取引先コード・別名に当たる作品が出る（`works/repository.ts` の `partyMatchSql`）。

## 11. 案件 › 条件ごと（作品別の条件一覧）

案件を開いたときの既定のタブ（`client/WorkLedger.tsx`。前の「工程表（表）」の置き換え）。

- 左で作品を選ぶと、その作品の条件だけになる（作品が混じる案件で条件を選びやすく）。作品ごとに 条件の本数・止まり・未払い。
- 1行＝条件1本。列は器から順に **取引先 → 基本契約 → 発注書（利用許諾条件書）→ 条件 → 実績 → 支払文書 → 支払**（2026-11）。
  複数回の条件は 実績・支払文書・支払 のセルに回ごとの行。取引先名・番号・金額は行に1回だけ。絞り：止まっている／未払い／食い違い／重複／払い切り。
- **上段 IN（当社が払う：発注・取得）／下段 OUT（当社が受け取る：許諾）** に分け、段ごとに列の見出しを付ける。
  OUT の列は 利用許諾条件書 → … → 計算書 → 入金。段の中は従来どおり作品（または取引先）でまとめる。
- 基本契約の段は、条件が載っている契約の根（個別契約・補助文書・発注書の器は親の基本契約）。単体契約は「単体契約」の札。
- 発注書の段：業務委託は発注書。**単体契約（業務委託契約書に条件が直接付いたもの）は契約書が発注書を兼ねる**ので「まだ」にしない。
  利用許諾は条件書（個別利用許諾条件書・出版利用許諾条件書・取り込んだ利用許諾契約書）。
- 次の文書へ（`client/mapLinks.ts`）：発注書・単体契約 →「→ 検収書を作る」（支払文書 › 発注書から検収書 をその発注書・単体契約で開く）、
  IN の利用許諾条件書 →「→ 計算書を作る」（作家 × 作品の利用許諾計算の台帳）。条件の番号・文書の番号・基本契約の番号はそれぞれの画面を開く。
  取引先ごと（`MatterBundles.tsx`）も同じ並び（発注書・条件書 → 条件 → 実績 → 支払文書 → 支払）と同じ行き先。
- セルを押すと、その段を前に出した「まとめて直す」が**ポップアップ**で開く（管理者）。右に保存前の試算。画面を移らずに直して閉じる。
- 「＋ 実績を入れる」（`EventEntryForm` をポップアップで。次の回に入れる。**入れると閉じずに次の条件へ進む**：押した行から表示順に、払い切りでない条件を続けて。
  「k / n 件目」「この条件は飛ばす」「ここで終わる」。行を選んで「実績を続けて入れる」で選んだ条件だけ）、「＋ 支払を立てる」（決定済みの検収書・計算書から。`POST /documents/:id/payment`）。
- 「＋ 条件を続けて足す」（絞っている作品、または作品の束の見出しから）：`ConditionEntryForm` をポップアップで。**登録しても閉じず**、同じ作品・同じ種類で
  次のフォームが出る（「n 本目」「登録した n：CL-…」「次も ◯◯ で」）。「1 本だけ」と OUT は案件に繋がらないので、ここで繋ぐ。
- 食い違い（drift.ts）は、条件のセルに「金額・日付が食い違い」、発注書・検収書・支払のセルに「納品日 10-25 ≠ 予定 10-20」のように**何と何が違うか**を出す。
  **支払期日の正は支払**（作る順番は 条件 › 発注書 › 実績 › 支払 › 検収書。検収書は支払の期日を印字する。支払が無いときだけ納品日から計算）。
- 行を選んで **食い違いをそろえる（表）**（`client/DriftMatrix.tsx`）：行＝条件 × 列＝段 の表。緑の列（条件・予定・実績・支払）が正で、ここを直す。
  灰色の列（発注書・検収書に焼き付いた値）は、直した正と違えば赤で「前 → 後」。上の共通の設定（決定日・担当者【ご連絡先】・訂正版（-Rn）か新規（下敷きにして作り、元を無効）か・
  下書きまでか決定までか・理由）を決め、「この内容で直して文書を作り直す」で一度に流す（行ごとに まとめて直す → 新規なら derive＋void → 担当者を入れて決定）。
  束ねた文書・同じ支払は1回だけ。訂正版を画面の外から決定するとき、実績は 渡されたもの → 下書きの `_eventIds` → 元の文書に付いている実績 の順で引く（issue-service）。
- 「＋ 支払を立てる」は、検収書が無くても実績から立てられる（`POST /payments/from-events`）。
- 同じ内容で重複している条件明細は行に「重複 n 本」が付き、押すとその場で畳める（どれを残すかは人が選ぶ）。
- 行を選んでまとめて（帯は選んでいる間は上に貼り付く）：**発注書を作る**／**検収書・計算書を作る**（ひな形を決めて開く）／**作業テーブルで作る（契約書・セット）**
  （選んだ条件を作業テーブルに渡す。基本契約・単体契約と発注書のセット、既にある文書を繋ぐ、外の文書の登録はそちら）／ほかのひな形で。いずれも **文書をまとめて作る**（1枚にまとめる＝選んだ条件を1枚に、宛先が1社のときだけ／取引先ごとに1枚＝複数人に／条件ごとに1枚。下書きまで。
  検収書のひな形なら、まだ載っていない実績を回ごとに拾う）、支払日をそろえる、未払いの支払を取り消す。
- ポップアップの実績の回ごとに「この実績を取り消す」（無効にする。理由は下の欄）。検収書・計算書に載っている実績は「検収書ごと取り消す」：
  先にその文書を無効にし（載っていたほかの実績は検収書なしに戻る。文書の無効は戻せる）、この実績だけ取り消す。
  支払が立っていれば文書の側で止まり（`POST /documents/:id/void` も `detail.blockingPayments` を返す）、その場で支払を取り消して続けられる（PaymentBlock）。

## 11b. 作品台帳 › 条件ごと

作品 1 点の条件を案件をまたいで 1 行ずつ（`GET /works/:id/grid`。列・ポップアップ・まとめての操作は案件の「条件ごと」と同じ `WorkLedger`）。
作品が 1 点なので左の作品の欄は無く、既定で取引先ごとにまとめる。重複の印（案件の中だけ）は出ない。
全作品の条件整理・契約整理はここから：作品を検索 → 条件ごと → 行を選んで 発注書・検収書・条件書（作業テーブル）・食い違いの表。

## 12. 条件明細の無効化の取り消し

無効化した条件は行が残るので戻せる（`POST /conditions/:id/unvoid`。条件明細の画面と作品の条件一覧（「無効化済みも」）の「無効を取り消す」）。
理由は必須で備考と監査（`condition.unvoid`）に残る。戻せないのは、同じ系列に生きた版があるとき（旧版を戻すと版が二重）と、
同じ 作品 × 相手先 × 向き × 種別 × 利用形態 × パート の生きた条件があるとき（重複整理で畳んだ側を戻すと二重）。
適用開始が未来なら「予約」に戻る。
