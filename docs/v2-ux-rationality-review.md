# V2 UI/UX 合理性レビュー — V1 の「迷いの構造」を踏まえた IA 設計指針

V1 は「ユーザーに迷いを生じやすい構造」だった。本レビューは V1 の迷いの発生源を類型化し、
**実際の作業フロー（誰が・何を・どの順で行うか）**に立ち返って V2 の現状を評価し、合理化の具体案を示す。
視覚スタイルではなく IA（情報設計）とワークフローに限定。

## 0. 実タスクフロー（＝設計の起点）

| ロール | 本当にやる仕事 | 必要な画面（最小） |
|---|---|---|
| **申請者** | 依頼を出す → 進捗を見る → 出来上がった文書を受け取る | 依頼状況・自分の文書/下書き のみ |
| **法務** | 依頼を捌く → 案件化 → 文書作成/確定 → 送信 → 検収・条件管理 →（名寄せ/品質保守） | 依頼→案件→文書→送信の主ループ＋条件/品質 |
| **管理者** | マスタ・設定・機能有効化・受信取込・監視 | マスタ/設定/ガイド/管理 |

→ **IA は「ロール優先 → タスクループ順」で構成すべき**。V1 は全員に全部（18項目＋保守モジュール）を見せ、この原則が崩れていた。

## 1. V1 の迷いの構造（5類型・要約）

1. **作業オブジェクトの三重帳簿**：案件 / 課題(`/issues/:key`) / 新課題(`/unified`) が親子でも代替でもなく部分的に重複し、機能完全度が違う。ユーザーは毎回「どれを開くか」を判断。
2. **暗黙モードの入口乱立**：`/documents/new` が 18ファイル39箇所から起動し、入口ごとに初期状態・自動補完・閲覧/編集モードが変わる。「正しい入口」を外すと手入力増・混在事故。検収も入口が4系統に分散。
3. **用語の不整合**：契約・条件明細・仕事単位が画面をまたぐと別名に。ブランド名/UI言語すらスキンで変動。ナビ説明文が実装と乖離（「マスタに契約」と書くが実際は移設済）。
4. **ロール未分岐**：`role` は右上ラベル表示のみ。ナビ/ルータにロールゲートゼロ＝閲覧者にも編集・統合・削除ボタンが常時露出（＝押してよいか不安＝hesitation）。
5. **巨大マルチ目的画面**：Editor 3,787行・MatterDetail 1,861行。日常操作と破壊的操作（統合・取り込み削除）が視覚的に等価に同居。

## 2. V2 現状評価

### ✅ すでに V1 病を治している点（**維持すべき資産**・退行させない）
- **作業オブジェクトを案件に正典化**（三重帳簿を廃し `matters` 単一モデル）。unified/issues 系は移植せず。
- **文書作成 funnel の統一**：案件詳細/依頼/検収待ち/ホーム/文書一覧の「作成」が**すべて `templates` に集約**し issueKey/seed を引き継ぐ（V1 の入口乱立の解）。
- **破壊操作のトークン型を完全統一**：取引先名寄せ・案件名寄せ・案件削除が「プレビュー表→合言葉→実行、旧は非破壊」で `vm-refs`/`vm-confirm` クラスまで共有。
- **ロールを一級市民化**：admin/legal/requester でナビを出し分け（V1 の未分岐を解消）。
- **Breadcrumb で現在地と親復帰**を全 view に提供。

## 3. 合理化の設計原則（V1 の反省を昇華）

1. **1タスク＝1正規入口＋文脈プリフィル**（入口ごとに挙動を変えない）。V2 の文書 funnel を全タスクの手本に。
2. **ロール優先ナビ**：申請者に保守・マスタ・財務を見せない。法務に主ループを、管理者に設定を。
3. **未有効化は「隠す」のではなく「1つの型で説明」**：どこで誰が有効化できるかを end-user 語で示す（GRANT番号は出さない）。
4. **発見と是正を繋ぐ**：品質スキャン→是正画面へ対象を引き継ぐ（prop 配線）。
5. **破壊度に比例したガード**：本番不可逆＝プレビュー＋合言葉／通常書込＝インライン確認。重み付けを揃える。
6. **語彙を1つの用語集に固定**し、ラベル/パンくず/API を一致させる。

## 5. 進め方の提案

1. **先に Quick Wins（Q1–Q4）**：低リスクで「迷い」を即低減。特に Q1（発見→是正）と Q2（未有効化＋GRANT番号除去）は体験改善が大きい。
2. **次にナビ再編（R1）＋ガード階層化（R4）**：IA の背骨を整える。
3. **Phase 10/11 の新規画面（アーカイブ/設定/承認ルート）着手時に B2 を適用**し、増える画面が再び散らからないようにする。
4. 「条件/作品」集約（R2/R3）と作成→出力1画面化（B1）は影響範囲が広いので、業務ヒアリングで実利用頻度を確認してからトリアージ。

> 本レビューは `docs/v1-v2-gap-remaining.md`（機能ギャップ）と対になる **体験（IA/UX）の台帳**。新規画面を足すたびに散らかった V1 に戻らないための設計指針として参照する。
